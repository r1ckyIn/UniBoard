  <action>
Create `supabase/migrations/00000000000002_rls_policies.sql` that enables RLS and creates CRUD policies for every table.

For each table, the pattern is:
```sql
ALTER TABLE {table} ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Users can view own {table}"
  ON {table} FOR SELECT TO authenticated
  USING ((select auth.uid()) = user_id);

CREATE POLICY "Users can insert own {table}"
  ON {table} FOR INSERT TO authenticated
  WITH CHECK ((select auth.uid()) = user_id);

CREATE POLICY "Users can update own {table}"
  ON {table} FOR UPDATE TO authenticated
  USING ((select auth.uid()) = user_id)
  WITH CHECK ((select auth.uid()) = user_id);

CREATE POLICY "Users can delete own {table}"
  ON {table} FOR DELETE TO authenticated
  USING ((select auth.uid()) = user_id);
```

Apply this pattern to ALL tables with a `user_id` column:
- courses
- grades (use `(select auth.uid()) = (SELECT user_id FROM courses WHERE id = course_id)` since grades don't have direct user_id -- OR add user_id to grades. IMPORTANT: Check if grades has user_id. It does NOT -- it references course_id. For tables without direct user_id (grades, modules, module_items, lessons, slides, unified_deadlines, discussion_threads, unit_outlines), use a subquery join through the courses table: `USING ((select auth.uid()) = (SELECT c.user_id FROM courses c WHERE c.id = course_id))`. For deeper nesting (module_items -> modules -> courses, slides -> lessons -> courses), chain the subquery.

Actually, for performance and simplicity, the better approach is: since Python backend connects with the postgres/service_role (bypasses RLS), and RLS primarily protects direct Supabase client access (which only happens for auth in this project), we should still add RLS on all tables but use a simpler approach:

For tables WITH direct `user_id`: courses -- standard `(select auth.uid()) = user_id` pattern.

For tables WITHOUT direct `user_id` but with `course_id` FK (grades, unified_deadlines, discussion_threads, modules, lessons, unit_outlines): use a subquery policy:
```sql
CREATE POLICY "Users can view own grades"
  ON grades FOR SELECT TO authenticated
  USING (course_id IN (SELECT id FROM courses WHERE user_id = (select auth.uid())));
```

For tables with deeper nesting (module_items -> modules -> courses, slides -> lessons -> courses):
```sql
CREATE POLICY "Users can view own module_items"
  ON module_items FOR SELECT TO authenticated
  USING (module_id IN (SELECT m.id FROM modules m JOIN courses c ON m.course_id = c.id WHERE c.user_id = (select auth.uid())));
```

For the `profiles` table: use `(select auth.uid()) = id` (since PK is auth.users id).

For tables with direct `user_id` column: digests, notifications, push_records, whatif_scenarios, content_embeddings. Apply standard pattern.

Create SELECT, INSERT, UPDATE, DELETE policies for every table using the appropriate strategy above.

Also add a `service_role` bypass comment explaining that the Python backend uses the postgres/service_role connection which bypasses RLS.

After creating the file, run `supabase db reset` to apply both migrations.
