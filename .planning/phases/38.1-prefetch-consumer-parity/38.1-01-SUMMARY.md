## Test Harness Design

### Three-bucket classification (load-bearing maintenance surface)

Every `use[A-Z]\w*` hook invocation found in a force-dynamic page's consumer must map into exactly one of:

- **HOOK_TO_FACTORY** (13 entries) — data-query hooks that must be prefetched; value is the queryOptions-factory dot-path that must appear in page.tsx
- **MUTATION_HOOKS** (10 entries) — mutations and disabled-query hooks that are exempt from prefetch
- **IGNORED_HOOKS** (32 entries) — React stdlib, next-intl, TanStack helpers, zustand selectors, project non-data hooks

The `no unknown bucket` audit test fails if any consumer introduces a fourth-bucket symbol.

### Deviations from PATTERNS.md §7 template (Rule 2 — correctness)

1. **Comment stripping on pageSource.** The plan's spec used a bare `pageSource.includes(factory)` check. Timetable's page.tsx header comment (L11: `//   - useQueries on courseOptions.detail(c.id)   -> N × detail`) contains the literal string `"courseOptions.detail"`, which would make the naive check falsely pass — producing a GREEN result for a page that genuinely lacks the prefetch. Added a `stripComments()` pre-pass that removes `/* ... */` blocks and `//` line comments before the `.includes()` check. This preserves the plan's RED-state contract for Timetable (`useCourseDetail (expected prefetch via courseOptions.detail)` in the failure message).

2. **Factory-reverse scan on consumers.** The plan expected the Timetable failure to name `useCourseDetail`, but TimetablePage.tsx never calls `useCourseDetail()` directly — it inlines `courseOptions.detail(c.id)` inside `useQueries({ queries: ... })`. Same pattern in PredictPage.tsx. The hook-call regex alone cannot see this, so a second pass scans consumer source for `xxxOptions.yyy(` matches and reverse-maps (`FACTORY_TO_HOOK`) to the original hook name. This lets Timetable and Predict correctly report missing `courseOptions.detail` prefetches under the hook identifier a developer recognises.

Both additions are narrowly scoped, fully documented with inline rationale in the test file, and do not change the plan's required output surface — they only make the test robust enough to produce that output reliably.

## IGNORED_HOOKS Allowlist Rationale

| Bucket | Members | Why ignored |
|---|---|---|
| React core | `useState, useEffect, useRef, useMemo, useCallback, useReducer, useContext, useLayoutEffect, useTransition, useDeferredValue, useId, useSyncExternalStore, useImperativeHandle, useDebugValue, useInsertionEffect, useOptimistic, useActionState, useFormStatus, useFormState` | Built-in non-data hooks |
| next-intl | `useTranslations, useLocale, useFormatter, useNow, useTimeZone, useMessages` | i18n helpers (no network) |
| next navigation | `useRouter, useSearchParams, usePathname, useParams` | Router state hooks |
| TanStack Query non-data | `useQueryClient, useQueries` | Client helper + fanout primitive (data fetch lives in the factories it wraps — handled by factory-reverse scan) |
| Project helpers | `useAuthStore, useCountUp` | zustand selector + pure animation hook |

No surprises surfaced during implementation — all 25 hooks found across the 6 consumer files classified cleanly into the three buckets on the first pass.
