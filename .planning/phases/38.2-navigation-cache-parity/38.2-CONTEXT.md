**Gathered:** 2026-04-22

<domain>
## Phase Boundary

Close the skeleton-flash gap that Phase 38 (first-load-performance) and Phase 38.1 (prefetch-consumer-parity) failed to fully close. Achieve: **hard-refresh any dashboard page on warm Railway → no full-page skeleton visible; client-side sidebar nav to any previously-visited page → zero loading state**.

Two architectural reversals and one operational activation, plus diagnostic cleanup. No new features, no new components, no new API endpoints, no changes to the RSC prefetch / HydrationBoundary contract from Phase 38.

</domain>

<decisions>
## Implementation Decisions

### force-dynamic removal (6 page.tsx files)

- **D-01:** Remove `export const dynamic = "force-dynamic"` from all 6 dashboard pages: `frontend/app/[locale]/(dashboard)/page.tsx` (Dashboard), `timetable/page.tsx`, `courses/page.tsx`, `deadlines/page.tsx`, `predict/page.tsx`, `digest/page.tsx`.
- **D-02:** Do **not** replace with `export const dynamic = "auto"` (the default) — omit the directive entirely. Next.js 15 auto-detects dynamic rendering when the route tree uses `cookies()` / `headers()` / `auth.getSession()`, which our HOF does unconditionally. Explicit `"auto"` is redundant noise.
- **D-03:** Do **not** add `export const fetchCache` override. Data fetching goes through `getServerApiClient` (ky, not Next.js `fetch`), so Next.js fetch cache is not in the data path. Router cache behavior is what we care about, and that's controlled by absence-of-`force-dynamic`, not `fetchCache`.

### loading.tsx removal

- **D-04:** Delete `frontend/app/[locale]/(dashboard)/loading.tsx` entirely. The file was added in PR #95 as a Suspense fallback for "instant route-transition feedback", but in the force-dynamic architecture it rendered the full-page skeleton layout during every server-side RSC wait, which is exactly the symptom users complained about on 2026-04-22.
- **D-05:** After deletion, route transitions rely on Next.js router cache (client-nav to cached pages → instant) + Next.js's default "keep old page visible until new RSC arrives" (client-nav to uncached pages → old page visible ~300 ms, then swap). Hard-refresh on a cold browser shows ~300 ms of browser-default loading indicator (URL bar spinner, blank content area) — **no skeleton** — before real data appears. This is the tradeoff we explicitly accept.

### Railway warmup activation

- **D-06:** Uncomment the `schedule:` block in `.github/workflows/railway-warmup.yml` (Phase 38-03 Plan shipped this infrastructure with `schedule:` commented-out pending the activation decision). Cron expression: `*/10 * * * *` — every 10 minutes, comfortably under Railway's 15-minute idle-shutdown threshold.
- **D-07:** Update `.planning/phases/38-first-load-performance/coldstart-report.md` to record the activation decision + date (checkbox in the decision rubric), even if the formal p50/p95 measurement (Phase 38-03 HUMAN-UAT item #2) is still pending. The measurement can still run post-activation to quantify improvement; activation doesn't block that.
- **D-08:** Do **not** add graceful degradation logic for "cron missed firing" scenarios. If a scheduled run fails, users see one cold start per window — rare, bounded, monitored via existing Sentry `operation:rsc_prefetch` tagging. Adding fallback logic would add code without addressing the core experience.

### Per-user data isolation (safety)

- **D-14:** Router cache is per-browser-session by construction (Next.js 15 router cache lives in the client's JS runtime, never shared across sessions/origins/browsers/users), so cross-user leak is structurally impossible in single-browser scenarios. Phase research (`gsd-phase-researcher`) must confirm this from Next.js 15 docs and flag any caveats (e.g., CDN interaction, shared-hosting scenarios).
- **D-15:** If research surfaces any caveat (e.g., a known Next.js 15 bug where router cache leaks through SharedWorker, or a CDN edge case with Vercel), the plan adds an explicit test or mitigation. Otherwise no code is needed for isolation — it's a framework guarantee.

Phase 38.2 doesn't change pixel-level layout — deleting `loading.tsx` changes **when** skeleton shows, not **whether** skeleton exists in any steady state. Existing baselines (when captured) will still apply. Phase 38.2's verification uses naked-eye UAT only, consistent with 38.1's approach.

<specifics>
## Specific Ideas

- **D-04 rationale (from inline discussion 2026-04-22):** User explicitly questioned the "500 ms skeleton after warmup" framing and pointed out that per their expectation, **after first load, subsequent navigations should have zero loading**. That insight drove the realization that `force-dynamic` was actively defeating Next.js router cache. Deleting `loading.tsx` is the user-approved tradeoff — they prefer "no skeleton ever" over "brief skeleton on hard refresh".
- **D-05 tradeoff (explicitly accepted):** On a truly cold Railway + empty browser cache hard-refresh, there will be a ~300 ms moment with no visual feedback beyond the browser URL bar spinner. This is deemed superior to showing a skeleton for the same 300 ms. Any performance measurement should confirm TTFB stays under 500 ms p95 with warmup active; if it drifts above that, we revisit.
- **D-06 cron interval choice (10 min):** Railway default idle timeout is 15 min; pinging every 10 min keeps a 5-min safety margin even if a cron run is delayed by GitHub Actions queue time (GHA cron has ~1-5 min jitter in practice).
- **Sentry trial-expired reality:** The diagnostic cycle that produced PR #100 / #101 / #103 partially succeeded only because we added `console.warn` checkpoints independent of Sentry (PR #103). Lesson carried into 38.2: the production-observability layer must not depend solely on Sentry trial availability. Revisit long-term Sentry plan post-38.2 (deferred, not in scope).

</specifics>
