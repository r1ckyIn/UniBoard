## force-dynamic removal

| Option | Description | Pros | Cons | Selected |
|---|---|---|---|---|
| Remove from all 6 | Delete `export const dynamic = "force-dynamic"` from every dashboard page.tsx | Router cache works; zero-latency revisits; addresses the UX root cause | Reverts Phase 38 Truth #1 contract (must document as SUPERSEDED) | ✓ |
| Remove from some | Keep for e.g. Dashboard but remove from sidebar pages | Partial optimization | Inconsistent architecture; defeats the purpose for the most-visited page | |
| Keep all; tune cache | Keep `force-dynamic`, add `experimental.staleTimes` overrides | Minimal change | Still triggers RSC re-run on every nav; loading.tsx still fires; doesn't address root cause | |

**User's choice:** Remove from all 6 (D-01).
**Notes:** The whole point of the user's "zero-latency revisit" expectation is that the client-side cache should serve revisits without server re-render. `force-dynamic` forcibly re-renders on every navigation, defeating this. Partial removal leaves the inconsistency; keeping all defeats the goal.

## Replacement directive

| Option | Description | Selected |
|---|---|---|
| Omit directive entirely | Let Next.js auto-detect dynamic rendering from `cookies()`/`headers()` usage | ✓ |
| `export const dynamic = "auto"` | Explicit default | |
| `export const dynamic = "force-static"` | Opposite extreme — static render | |

**User's choice:** Omit entirely (D-02).
**Notes:** `"auto"` is the default; explicit declaration is noise. `"force-static"` would break auth-dependent pages (Next.js would error during build or at runtime when `cookies()` is called in a static context).

## loading.tsx fate

| Option | Description | Pros | Cons | Selected |
|---|---|---|---|---|
| Delete entirely | Remove `frontend/app/[locale]/(dashboard)/loading.tsx` | No more full-page skeleton; relies on browser default + Next.js "keep old page visible" | Brief blank during hard-refresh cold start | ✓ |
| Keep as-is | No change | Suspense fallback fires instantly | The exact symptom users complained about | |
| Replace with subtle indicator | Replace SkeletonCard layout with a thin top bar / small spinner | Minimal visual noise; still provides feedback | Adds new component; still shows SOMETHING during the wait | |

**User's choice:** Delete entirely (D-04).
**Notes:** User explicitly stated preference for "no skeleton ever" over brief skeleton. Next.js's default behavior (keep old page visible during client-side nav, brief blank during hard-refresh) is acceptable. If post-deploy UAT finds the blank moment objectionable, we can revisit with a subtle indicator in a follow-up phase; starting conservative with a clean deletion is preferred.

## Warmup cron interval

| Option | Description | Pros | Cons | Selected |
|---|---|---|---|---|
| Every 5 min | Max aggressive warmth | Tightest cold-start prevention | More GHA minutes; borderline abusive of free tier | |
| Every 10 min | 5-min safety margin below Railway's 15-min idle timeout | Balanced; tolerant to GHA cron jitter | — | ✓ |
| Every 15 min | Exactly at idle timeout boundary | Minimum cost | No jitter margin; risks cold starts if cron delays | |

**User's choice:** 10 min (D-06).
**Notes:** Railway idle timeout is 15 min. GitHub Actions cron has documented ~1-5 min jitter under load. 10-min interval gives 5-min safety margin and 6 runs/hour (144/day) is comfortably within free tier quotas.

## Per-user cache isolation (safety)

| Option | Description | Selected |
|---|---|---|
| Trust framework + research to verify | Have gsd-phase-researcher confirm Next.js 15 router cache is per-session-only; add test if research finds a caveat | ✓ |
| Add mandatory regression test | Write a test that cycles two mock users and asserts no cache leak | |
| Skip verification | Trust the framework without research | |

**User's choice:** Research-verify (D-14 + D-15).
**Notes:** Router cache is client-side per-browser-session by construction in Next.js 15 — it's not a persistent or cross-session cache. Cross-user leak requires either (a) a framework bug, which research can surface, or (b) shared-browser scenarios (e.g., two users on the same physical machine), which are out of scope for web app threat modeling. Research + a conditional test (added only if research finds something) is proportionate.
