# Phase 38.2 Learnings: Navigation-Cache ↔ Skeleton-Free Parity (Architectural Correction)

## Decisions

### Remove `force-dynamic` from all 6 dashboard pages
Deleted `export const dynamic = "force-dynamic"` from Dashboard / Timetable / Courses / Deadlines / Predict / Digest page.tsx files. Do not replace with `"auto"` — omitting the directive lets Next.js auto-detect dynamic rendering from `cookies()`/`headers()`/`auth.getSession()` usage.

**Rationale:** `force-dynamic` forces server RSC + prefetch on every navigation, defeating Next.js 15 router cache and producing the full-page skeleton flash the user observed.
**Source:** 38.2-CONTEXT.md §D-01/02/03, debug session sidebar-nav-skeleton-stall.md

### Delete `app/[locale]/(dashboard)/loading.tsx` entirely
Removed the Suspense fallback file added in PR #95. Next.js keeps the old page visible during client-side nav (no skeleton) and shows browser-default loading indicator for ~300 ms during hard-refresh.

**Rationale:** `loading.tsx` was faithfully rendering full-page skeleton during the server RSC wait — the exact symptom users complained about. User explicitly chose "no skeleton ever" over brief skeleton.
**Source:** 38.2-CONTEXT.md §D-04/05, user verbal approval inline during 2026-04-22 session

### Add `experimental.staleTimes.dynamic: 30` to next.config.ts
Required escape hatch for Next.js 15's router cache to work on dynamic routes.

**Rationale:** Research R1/R6 discovered Next.js 15.0.0 changed `experimental.staleTimes.dynamic` default from 30s → 0s. Without this config, removing `force-dynamic` alone achieves nothing — every navigation still runs server RSC. This was in CONTEXT's "Deferred Ideas" but research promoted it to MANDATORY.
**Source:** 38.2-RESEARCH.md §R1 + §R6, Next.js 15 release blog

### Fix `/healthz → /health` in 4 files
Railway backend exposes `/health`, not `/healthz`. Updated railway-warmup.yml, railway-coldstart-measure.yml, frontend/tests/e2e/perf/measure-coldstart.ts, frontend/tests/e2e/perf/coldstart.spec.ts.

**Rationale:** Pre-existing Phase 38-03 bug that would have caused warmup cron to silently 404 every 10 minutes once activated. Research R5 found this via live curl verification.
**Source:** 38.2-RESEARCH.md §R5, src/web/routes/health.py

### Activate Railway warmup cron at 10-min interval
Uncommented `schedule: - cron: "*/10 * * * *"` in railway-warmup.yml.

**Rationale:** Railway's default idle timeout is 15 min. 10-min interval gives 5-min safety margin for GitHub Actions cron jitter. Was Phase 38-03 deliverable; 38.2 activates it.
**Source:** 38.2-CONTEXT.md §D-06

### APPEND-ONLY VERIFICATION annotation, not inline edit
Added `SUPERSEDED BY 38.2` footer below Observable Truths table in Phase 38 VERIFICATION.md. Original Truth #1 row byte-identical.

**Rationale:** Phase 38 Truth #1 was accurate when VERIFIED. Editing inline would destroy audit trail of "what was the original intent, why did it change". Append-only preserves both.
**Source:** 38.2-CONTEXT.md §D-12

### Two-plan partition over monolithic
Split 14-file change into Plan 01 (frontend/) + Plan 02 (.github/workflows/ + .planning/) with zero files_modified overlap.

**Rationale:** Enables true parallel executor execution (two worktrees, no lock contention). PATTERNS.md recommended monolithic initially; planner chose the 2-plan alternative for parallelism without sacrificing atomicity.
**Source:** 38.2-01-PLAN.md, 38.2-02-PLAN.md

### Remove diagnostic breadcrumbs from HOF (not flag-gate them)
Deleted `diagLog` helper + all 5 call sites + 3 `Sentry.captureMessage` calls + `headers` import. HOF reverted to 155 lines (Phase 38 baseline shape from ~300 lines).

**Rationale:** The 3 diagnostic PRs (#100/#101/#103) were explicitly "temporary". Keeping flag-gated diagnostic code is maintenance burden; future diagnostics should be tailored to whatever bug is being investigated, not generic.
**Source:** 38.2-CONTEXT.md §D-09/10/11

## Lessons

### Phase 38's `force-dynamic` + `loading.tsx` was a compound bug
Neither alone was the problem; together they transformed server wait into user-visible skeleton.

**Context:** `force-dynamic` makes every navigation re-run server RSC (expected; Phase 38 design intent). `loading.tsx` as Suspense fallback was added later (PR #95) intending "instant feedback". Together they guarantee users see skeleton for the full server-RSC duration on every nav. Fixing either alone would leave ~half the problem.
**Source:** 38.2-CONTEXT.md §Context + debug session analysis

### Next.js 15.0.0 silently shipped a default change (`staleTimes.dynamic: 30s → 0s`)
Without explicit `experimental.staleTimes` config, router cache for dynamic routes is effectively off.

**Context:** This isn't in the Next.js 14 → 15 migration guide prominently. Research R1 only surfaced it after reading the release blog + staleTimes Version History page. Had we not researched, Phase 38.2 would have shipped a half-win (force-dynamic gone, but cache still off → same skeleton problem).
**Source:** 38.2-RESEARCH.md §R1/R6

### Sentry trial expiry invisibly degraded production observability
Events from RSC context stopped appearing 2026-04-19, but we didn't notice until adding diagnostic breadcrumbs returned zero results.

**Context:** `reference_sentry_config.md` memory noted the expiry date, but no alert fired when event volume dropped to zero. Had we been paying attention to Sentry dashboards daily, we'd have caught this proactively. Production observability must not depend solely on one vendor or trial status.
**Source:** Vercel Logs diagnostic cycle, PR #103 `[RSC_DIAG]` fallback

### Pre-existing cross-phase bugs can hide for weeks
The `/healthz` vs `/health` mismatch was introduced in Phase 38-03 (2026-04-XX). Because the warmup cron's `schedule:` block was commented out, the bug never manifested. Once activation was planned, live curl verification caught it.

**Context:** Infrastructure that "works" only when disabled isn't verified. Activation gates should include a live-run smoke test, not just YAML validation.
**Source:** 38.2-RESEARCH.md §R5 live curl verification

### Agent-browser `--auto-connect` changed debugging velocity
Using the user's running Chrome (with their auth state) to drive UI + logs simultaneously is dramatically faster than spawning Playwright from scratch or asking user to screenshot.

**Context:** The 2026-04-22 diagnostic cycle tried Sentry (failed — trial expired), then Vercel Logs (worked via console.warn fallback), then agent-browser (worked immediately and captured the full production state). Each layer of automation collapsed ~15 minutes of interaction into real-time observation.
**Source:** Real-time capture of Dashboard hard-refresh at T+300/800/1800/3800ms confirming loading.tsx was the culprit

### Research-before-planning catches scope gaps CONTEXT misses
38.2-CONTEXT.md classified `experimental.staleTimes` as a deferred idea. 38.2-RESEARCH.md promoted it to mandatory based on Next.js 15 docs. Similarly /healthz fix was not in CONTEXT at all.

**Context:** CONTEXT gathers what the user knows; RESEARCH surfaces what the framework/infra will make you learn. Phases that skip research (`--skip-research` or `--gaps`) risk these gaps.
**Source:** 38.2-RESEARCH.md vs 38.2-CONTEXT.md

## Patterns

### Two-executor parallel wave with disjoint files_modified
When a phase's changes split cleanly across two directory trees (e.g., `frontend/` vs `.github/workflows/`), partition into two plans with zero file overlap and run both in parallel worktrees.

**When to use:** Any phase where changes cluster into distinct layers (frontend src vs infra, UI vs backend, etc.) and the clusters don't share files. Halves wall-clock execution time vs monolithic.
**Source:** 38.2-01-PLAN.md + 38.2-02-PLAN.md, executed in same Wave 1

### Research-driven MUST-DO promotion
If research surfaces a technical requirement that CONTEXT didn't anticipate (e.g., a framework quirk, a pre-existing bug, a default-value change), the planner MUST fold it into scope. Not adding it would invalidate the phase's stated success criteria.

**When to use:** Any phase with RESEARCH.md that identifies "DEV-N MUST-DO" items. Document the reasoning in PLAN.md so code-reviewer + verifier can verify the promotion was correct.
**Source:** DEV-1 (staleTimes) + DEV-2 (/healthz fix) promoted from CONTEXT deferred → mandatory via 38.2-RESEARCH.md

### APPEND-ONLY annotation for reversed decisions
When a later phase reverses a prior phase's design decision, annotate the prior phase's VERIFICATION.md via append-only footer, not inline edit. Preserves audit trail.

**When to use:** Any architectural reversal across phases. Do NOT edit the reversed Truth's text — that destroys "why we changed it" evidence. Annotate BELOW the Observable Truths table.
**Source:** 38.2-CONTEXT.md §D-12 + 38-VERIFICATION.md SUPERSEDED footer

### Console-warn diagnostic bypass when vendor observability is degraded
If Sentry/Datadog/etc. is unreliable (trial expired, quota exhausted, SDK misconfigured), add `console.warn(JSON.stringify(...))` checkpoints that land in runtime logs (Vercel Functions, CloudWatch, Railway). Prefix with a grep-friendly tag.

**When to use:** Production debugging when primary observability pipeline is suspect. Write a structured tag (`[RSC_DIAG] event_name {json}`) so you can filter in log viewer.
**Source:** PR #103 `[RSC_DIAG]` helper in create-prefetched-page.tsx

### Agent-browser `--auto-connect` for production UAT with real auth
Connect to the user's running Chrome (with their live session cookies) to drive UI navigation + simultaneously scrape logs/dashboards from Vercel/Sentry/etc. Eliminates "paste me a screenshot" round-trips.

**When to use:** UI/UX bugs requiring real production state + real authenticated user + real-time observation. Requires Chrome started with `--remote-debugging-port=9222` (which UniBoard's Chrome already has).
**Source:** 2026-04-22 debugging session, captured T+300/800/1800/3800ms screenshots that pinpointed loading.tsx as the visual culprit

### CI path filter for Playwright on non-UI PRs
Use `dorny/paths-filter@v3` to conditionally skip heavy visual-regression CI jobs when the PR doesn't touch UI files. Saves ~2m per iteration on backend/config/doc PRs.

**When to use:** Any repo where Playwright (or similar heavy CI) runs on every frontend PR but isn't needed for non-visual changes. Define the UI path list narrowly (app/, components/, styles/, configs).
**Source:** PR #102 frontend-ci.yml gate

### Diagnostic code with pre-scheduled cleanup commit
When adding temporary diagnostic code (console.warn, Sentry.captureMessage, debug breadcrumbs), create a follow-up ticket/phase that commits to removing it. Don't let "temporary" become permanent.

**When to use:** Any diagnostic PR. Include a TODO with expiration date or a linked follow-up PR. 38.2 explicitly scoped the cleanup of PR #100/#101/#103 diagnostics as part of the architectural correction.
**Source:** 38.2-CONTEXT.md §D-09/10/11

## Surprises

### Research found 2 MUST-DOs that CONTEXT had deferred
`experimental.staleTimes.dynamic: 30` was in CONTEXT's "Deferred Ideas" section; research proved it mandatory. `/healthz → /health` wasn't in CONTEXT at all; research found it via live verification.

**Impact:** 38.2-RESEARCH.md added both to scope before planning started, so PLAN.md captured them atomically. Had research been skipped, 38.2 would have shipped a half-win + a silently-broken warmup cron. Reinforces "research enabled" as default for architectural phases.
**Source:** 38.2-RESEARCH.md §R1 + §R5

### Phase 38 VERIFICATION Truth #1 was VERIFIED-but-wrong
Truth #1 claimed "All 6 pages declare `force-dynamic`" as VERIFIED, and indeed the code did. But the decision itself was architecturally wrong for the stated goal (skeleton-free UX). Verification checked "code matches contract", not "contract delivers goal".

**Impact:** Documents the gap between implementation compliance and UX correctness. Future verifier should include a "does this contract actually deliver the ROADMAP goal?" check, not just "does the code match the contract". Captured as SUPERSEDED BY 38.2 footer.
**Source:** 38-VERIFICATION.md Truth #1 + 38.2 architectural reversal

### Code review returned PASS with 0 findings — third consecutive phase
38, 38.1, 38.2 all had `gsd-code-reviewer` return zero findings. Suggests the planner + pattern-mapper + research pipeline produces concrete-enough PLAN.md that executors don't drift.

**Impact:** Can we deprecate the code-review step for phases with high-discipline plans? Probably no — it's cheap and catches regressions, but the fact that it's finding nothing suggests the planner output quality is very high. Keep it as a defense-in-depth layer.
**Source:** gsd-code-reviewer return for 38.2, matching 38.1 pattern

### End-to-end 38.2 pipeline: "架构重制是不是要开一个新phase" → merged PR ≈ 2 hours
Discuss + research + pattern-map + plan + plan-check + execute (parallel) + code-review + verify + ship = sub-2-hour cycle. Faster than 38.1's ~3-hour cycle.

**Impact:** Architectural correction phases with clear CONTEXT + disciplined executors move much faster than features. The 38.1 pattern ("TDD RED → parallel plans flip to GREEN") was faster than 38; 38.2 ("2 disjoint plans parallel") was faster than 38.1. Each iteration getting better.
**Source:** git log timestamps + PR #104 mergedAt

### Sentry trial expiry was a session-altering constraint
The 2026-04-22 diagnostic session had to pivot twice because Sentry events weren't being captured. First pivot: added `console.warn` fallback in PR #103. Second pivot: used agent-browser + Vercel Logs instead of Sentry Issues. Lost ~30 minutes to the pivots.

**Impact:** Don't let observability become a single point of failure. Have a fallback plan for Sentry outages/trial expiry. Reinforces "production obs must be multi-channel" lesson.
**Source:** 2026-04-22 session transcript, PR #103 commit message
