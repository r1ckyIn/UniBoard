## Per-Question Deep Dive

### R1. Router Cache TTL for dynamic routes without `force-dynamic`

**Finding [HIGH CONFIDENCE]:**

Next.js 15.0.0 changed the default `experimental.staleTimes.dynamic` value from **30 seconds (v14.2)** to **0 seconds (v15+)**. This is a breaking change from the Next.js 15 release notes:

> *"In Next.js 15, this flag still remains accessible, but we are changing the default behavior to have a `staleTime` of `0` for Page segments. This means that as you navigate around your app, the client will always reflect the latest data from the Page component(s) that become active as part of the navigation."* — [Next.js 15 Release Notes](https://nextjs.org/blog/next-15#caching-semantics)

The official staleTimes docs confirm:
- **`dynamic` default: 0 seconds (not cached)** — applies when page is neither statically generated nor fully prefetched via `prefetch={true}`
- **`static` default: 5 minutes** — applies to statically generated pages or when `<Link prefetch={true}>` or `router.prefetch()` is called
- **`v14.2.0`: dynamic default was 30s**; **`v15.0.0`: changed to 0s** ([Version History in docs](https://nextjs.org/docs/app/api-reference/config/next-config-js/staleTimes))

**What this means for Phase 38.2:**

The 6 dashboard pages call `supabase.auth.getSession()` inside `createPrefetchedPage`. This calls `cookies()` implicitly (via `@supabase/ssr`). Per Next.js 15, this opts the route into dynamic rendering:

> *"Dynamic signals that turn a tree dynamic include the use of `cookies()`, `headers()`, authorization headers, or segment config options like `dynamic = 'force-dynamic'`."*

After D-01 (force-dynamic removal), the 6 pages will STILL be dynamic routes (due to cookies()). They will therefore fall under `staleTimes.dynamic`, which defaults to **0 — effectively NOT cached client-side**.

**Implication for user's "zero-latency revisit" goal:**

Without `experimental.staleTimes.dynamic: 30` in next.config.ts, CONTEXT.md D-01+D-04 alone will NOT deliver zero-latency revisits. Every sidebar click will still re-render the RSC server-side. The difference vs. current state is:

| Scenario | Current (force-dynamic + loading.tsx) | After D-01/D-04 only | After D-01/D-04 + staleTimes.dynamic:30 |
|----------|---------------------------------------|----------------------|------------------------------------------|
| Sidebar click to new page | Full skeleton flash during RSC wait (~200-500ms) | Old page stays visible during RSC wait (Next.js "keep old page" default), then swap to new page with prefetched data (still a click-to-swap delay) | Within 30s of last visit: **instant cache-hit swap, no server round-trip** |
| Sidebar click to previously-visited page within 30s | Full skeleton flash | Old page stays visible during RSC wait | **Instant cache-hit** |
| Hard refresh | Full skeleton flash | ~300ms browser-default loading state | ~300ms browser-default loading state (cache does not persist across hard refresh) |

**Recommendation [MUST-FIX scope addition]:**

Add to `frontend/next.config.ts`:

```typescript
const nextConfig: NextConfig = {
  // ... existing config ...
  experimental: {
    staleTimes: {
      dynamic: 30,   // restore v14 behavior: cache dynamic pages for 30s
      static: 180,   // 3 min for static/prefetched (explicit — default is 300, safe to omit)
    },
  },
};
```

### R2. Per-user data isolation in the router cache

**Finding [HIGH CONFIDENCE]:**

The Next.js Client Router Cache is:
1. **In-memory only** — lives in the browser's JavaScript runtime for the duration of the tab's page life. No localStorage, no IndexedDB, no cookies.
2. **Tab-scoped** — each tab has its own router cache instance. Opening a new tab creates a fresh instance. Cross-tab communication would require SharedWorker / BroadcastChannel which the Next.js framework does not use.
3. **Hard-refresh-invalidated** — closing and reopening the tab, or Cmd+Shift+R hard refresh, discards the entire in-memory cache.
4. **Cross-user isolation by construction** — because the cache is tab-JS-scoped, there is **no framework-level mechanism for User A's data to reach User B's tab**.

From the Next.js docs on Client Cache:
> *"A separate in-memory cache, split by individual route segment, which improves the navigation experience by storing previously visited routes and prefetching future routes."* — [Caching docs](https://nextjs.org/docs/app/guides/caching)

**The only leak vector in-scope for analysis: same-tab logout→login.**

User A logs out → Supabase `signOut()` clears localStorage + cookies + fires `SIGNED_OUT` event. User B logs in on the same tab → new Supabase session. However, the **router cache entries from User A's session could still be valid for up to 30 seconds** (if `staleTimes.dynamic: 30` is set per R1). On User B's first nav to a dashboard page, Next.js might serve User A's cached RSC payload.

**Verification via repo audit:**

- `frontend/components/layout/DashboardGuard.tsx:54` calls `router.replace(`/${locale}/auth`)` on logout (not-authenticated state). `router.replace` triggers a full navigation — this **does invalidate router cache entries for the old route**.
- `frontend/components/layout/Header.tsx` (inferred from 38.1-LEARNINGS + MEMORY.md ref to `useDeleteAccount`) calls `supabase.auth.signOut()` then `router.replace('/auth')`.

**Conclusion:**

Current logout flow already triggers `router.replace()` which invalidates the relevant router cache segments. **No additional code is needed** for isolation in 38.2, BUT the plan-checker should verify that:

1. `router.refresh()` is also called after signOut (belt-and-braces — clears all router cache, not just one segment). Community pattern: `signOut() → queryClient.clear() → router.refresh()`.
2. The logout flow doesn't rely on a path that depends on cached RSC payload.

**Defensive hardening (recommended for plan inclusion if trivial):**

In `frontend/lib/auth/signout.ts` (or wherever the logout helper lives — grep for `supabase.auth.signOut`), add after signOut:

```typescript
// Invalidate router cache so the next user on this tab doesn't see cached RSC
// payload from the previous session. See Phase 38.2 R2.
router.refresh();
queryClient.clear();  // TanStack Query — clear ALL queries, not just invalidate
```

If this call site doesn't already exist, **this is a modest 3-4 line hardening** the planner may choose to include in scope. Alternative: document as residual risk and defer; in practice, the attack surface is niche (shared-browser lab/family scenario).

### R3. Vercel Edge / CDN interaction with non-force-dynamic auth routes

**Finding [HIGH CONFIDENCE]:**

Vercel's CDN explicitly refuses to cache responses meeting any of the following conditions (from [Vercel CDN Cache docs — Cacheable response criteria](https://vercel.com/docs/cdn-cache#cacheable-response-criteria)):

- Request contains `Authorization` header ← **RSC loopback to `/api/v1/*` uses this**
- Response contains `set-cookie` header ← **Supabase auth responses set this**
- Response contains `private`, `no-cache`, or `no-store` directive ← **Next.js 15 `force-dynamic` sets `no-store`; even after removal, Supabase session cookies don't enable caching**

**In plain language:** there is no scenario where Vercel's CDN would Edge-cache a rendered dashboard RSC response and serve it to a different user. This holds both with and without `force-dynamic`.

**One caveat:** The BFF proxy routes at `frontend/app/api/v1/*` forward Authorization to Railway. The BFF route handlers themselves are also protected by the auth header requirement — they're never CDN-cacheable. No changes needed.

**Conclusion:**

Phase 38.2 introduces no new CDN-level risk. D-15 (no explicit test needed) is correct.

### R4. React Streaming + absence of `loading.tsx`

**Finding [HIGH CONFIDENCE]:**

Next.js 15 official docs on dynamic-route navigation without `loading.tsx` ([Linking and Navigating guide](https://nextjs.org/docs/app/getting-started/linking-and-navigating)):

> *"### Dynamic routes without `loading.tsx`*
> *When navigating to a dynamic route, the client must wait for the server response before showing the result. This can give the users the impression that the app is not responding."*

> *"### Client-side transitions*
> *[...] Instead of reloading the page, it updates the content dynamically by:*
> *- Keeping any shared layouts and UI.*
> *- Replacing the current page with the prefetched loading state or a new page if available."*

**What this means for Phase 38.2:**

**Client-side navigation (Link click from sidebar):**
- Old page stays visible during the server RSC wait (Next.js default).
- On RSC arrival, page swaps in with hydrated data (no skeleton, no blank).
- If `staleTimes.dynamic: 30` is set and user revisited within 30s → instant swap from router cache (no server wait).
- **User experience:** smooth, no skeleton, no blank.

**Hard refresh (browser reload):**
- Browser shows its native URL-bar spinner.
- Body area is blank (white) during server wait.
- Next.js does NOT stream a parent `loading.tsx` fallback because there is no parent loading.tsx (verified via Glob: `frontend/app/**/loading.tsx` returned only the `(dashboard)/loading.tsx` we're deleting).
- On RSC arrival, full page renders with hydrated data.
- **User experience:** ~300-500ms of blank body + browser's native loading indicator, then page renders.

**Parent loading.tsx inheritance check:**

```bash
# Verified via Glob — only one loading.tsx exists in the repo (the one we're deleting)
frontend/app/[locale]/(dashboard)/loading.tsx   ← to delete
# No frontend/app/loading.tsx, no frontend/app/[locale]/loading.tsx
```

**D-05 tradeoff is correct:** ~300ms of browser-default blank state on hard-refresh is the accepted cost for "no skeleton ever" on sidebar navigation.

### R5. Railway warmup — keep-alive semantics + monitoring

**Finding [MEDIUM-HIGH CONFIDENCE]:**

Railway's "Serverless" (formerly "App Sleeping") feature:

- **Idle threshold:** Docs say 10 minutes. Blog post (Railway launch announcement) also says 10-15 minute window.
- **Activity metric:** **OUTBOUND packets** from the service (not inbound HTTP requests).
- **Implication:** An `HTTP GET /healthz` request to Railway does NOT directly reset the idle timer — but if the health endpoint handler makes outbound calls (DB query, Redis ping, upstream API check), those outbound packets DO reset the timer.

From Railway docs ([Serverless reference](https://docs.railway.com/reference/app-sleeping)):

> *"For Railway to put a service to sleep, a service must not send outbound traffic for at least 10 minutes. Inbound traffic is excluded from considering when to sleep a service."*

> *"Anything that sends packets (DB connection pools, telemetry, scheduled pings, calls to other services) will keep the service awake."*

**Implication for the D-06 warmup cron:**

The warmup cron pings the backend health endpoint. If the health handler performs an outbound action (DB query, external API check), the cron DOES keep Railway warm. If the handler is a static "OK" response with no outbound calls, the cron is useless.

**Verified via repo audit (`src/web/routes/health.py:16-42`):**

```python
@router.get("/health")
async def health_check(session: AsyncSession = Depends(get_session)) -> JSONResponse:
    # ...
    await session.execute(text("SELECT 1"))  # ← OUTBOUND DB query
    # ...
```

**The `/health` endpoint executes `SELECT 1` against Supabase PostgreSQL — an outbound packet**. The warmup cron will effectively keep Railway warm. Good.

**HOWEVER — the critical bug (MUST-FIX #1):**

- `railway-warmup.yml:41` hits `${RAILWAY_URL%/}/healthz` (with `z`)
- `railway-coldstart-measure.yml:...` and `measure-coldstart.ts:35` also hit `/healthz` (with `z`)
- `coldstart.spec.ts:32` also hits `/healthz` (with `z`)
- Backend defines `/health` (no `z`) — verified in `src/web/routes/health.py:16` (`@router.get("/health")`)

**This is a pre-existing bug from Phase 38-03 that D-06 activation MUST fix.** If 38.2 activates the cron without this fix, the cron will fire every 10 minutes but receive 404 responses. Railway will still sleep. User's expectation is defeated.

```typescript
  experimental: {
    staleTimes: {
      dynamic: 30,   // seconds — applies to cookies()/headers() routes
      static: 180,   // seconds — applies to prefetched links + static routes
    },
  },
};
```

Key semantics:

1. **Feature marker: experimental.** Docs say *"This feature is currently experimental and subject to change, it is not recommended for production."* — but the feature has been in the product since 14.2 (Q1 2024) and has a clear migration path; multiple production apps use it. Low risk to adopt.

2. **`dynamic` property applies when:** page is neither statically generated nor fully prefetched via `prefetch={true}`. The 6 dashboard pages will fall into this bucket (dynamic due to cookies(), NOT prefetched fully even with `<Link prefetch>` because they're dynamic routes).

3. **`static` property applies when:** page is statically generated OR when `<Link prefetch={true}>` is used OR `router.prefetch()` is called. After PR #96, the sidebar uses `<Link prefetch={true}>` — but the docs say dynamic routes with `prefetch={true}` get "partial prefetch" (only the layout + loading skeleton), not the full `static` staleTime.

4. **Minimum enforced 30s for prefetched content** — per multiple community sources, the client router enforces a 30-second minimum staleTime for prefetched routes "to ensure prefetched links remain usable." Setting `dynamic: 0` still gives 30s for prefetched links.

5. **Partial rendering invariant preserved** — *"This doesn't affect partial rendering, meaning shared layouts won't automatically be refetched on every navigation, only the page segment that changes."*

6. **Back/forward cache preserved** — *"This doesn't change back/forward caching behavior to prevent layout shift and to prevent losing the browser scroll position."*

**Recommended config for Phase 38.2:**

```typescript

  staleTimes: {
    dynamic: 30,   // Phase 38.2: restore v14 behavior to enable zero-latency revisits
    // static: default 300 (5 min) — omit to keep default
  },
},
```

### R7. Edge case — logout flow

**Finding [MEDIUM CONFIDENCE]:**

Supabase `signOut()`:
- Clears localStorage + cookies
- Fires `SIGNED_OUT` event to subscribed listeners
- Does NOT automatically clear Next.js router cache or TanStack Query cache — that's the app's responsibility

Community-documented best practice for Next.js 15 + Supabase + TanStack Query logout:
```typescript
async function handleLogout() {
  await supabase.auth.signOut();
  queryClient.clear();           // clear ALL TanStack Query data (not just invalidate)
  router.refresh();              // invalidate Next.js router cache
  router.replace('/auth');       // redirect
}
```

**Repo audit (what exists today):**

- `frontend/components/layout/DashboardGuard.tsx:54` — `router.replace(`/${locale}/auth`)` on not-authenticated. This replaces the current route; router cache entries for the old route are invalidated (router.replace has this effect).
- `frontend/hooks/use-delete-account.ts` (inferred name from MEMORY.md) — calls signOut, then redirect.

**Gap analysis:**
- No `queryClient.clear()` call on logout → TanStack Query cache may retain stale user data until component unmounts.
- No explicit `router.refresh()` call → router cache MAY retain stale RSC payloads for up to `staleTimes.dynamic` seconds after logout.

**Severity assessment:**
- Low (single-user scenario — user logs out, cached data never leaves their own device).
- Medium (shared-browser scenario — user A logs out on family laptop, user B logs in same tab within 30s).

**Recommendation:**
- **Include in Phase 38.2 plan (small addition):** audit logout paths, add `queryClient.clear() + router.refresh()` if missing.
- **Defer (if plan scope tight):** document as known limitation + residual risk for v3.0; revisit in a future auth-hardening phase.

Planner's call; prefer the small-scope inclusion if the logout call site is a single function.
