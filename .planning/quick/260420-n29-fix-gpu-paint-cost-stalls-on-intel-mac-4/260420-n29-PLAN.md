The decisive user clue across all four main fixes was "窗口越小越流畅"
(smaller viewport = smoother). Paint cost scales O(w × h) on the Intel Mac
GPU raster pipeline. `requestAnimationFrame` keeps ticking at 60 Hz even
when the compositor has fallen to 2-5 fps, so rAF / LoAF synthetic
benchmarks completely miss these bugs — they only manifest on real-screen
frame delivery under large viewport.

Four subtypes shipped this session, one supporting CSP change:

| # | Subtype | Fix | PR |

| 1 | `backdrop-blur-[18px]` on sticky full-viewport header | Drop blur, raise bg alpha .82 → .97 | #89 |

PR #89 (commit 53623a3) removed `backdrop-blur-[18px]` from the sticky
`<header>` element in `frontend/components/layout/Header.tsx` and raised the
background alpha from `rgba(250,249,245,.82)` to `rgba(250,249,245,.97)` so
the frosted-glass look persisted without backdrop-filter's O(w × h) GPU
raster pass. The Header is the top-level layout chrome — any paint
invalidation under it (sidebar hover, route change, scroll) previously
forced the entire backdrop region to re-rasterise at full viewport width,
which on Intel Mac manifests as 2-5 fps with rAF still ticking at 60 Hz. A
multi-line inline comment was added directly above the `<header>` return
warning future maintainers not to re-introduce `backdrop-blur-*` on full-
viewport elements.

PR #90 (commit 38b5e68) replaced the sidebar's
`shadow-[2px_0_16px_rgba(20,20,19,.06)]` — which bled ~18 px into main
content OUTSIDE the `[contain:layout_paint]` box — with a
`border-r border-[rgba(20,20,19,.08)]` that paints INSIDE the contain
region. Because the sidebar's `width` animates on hover
(`var(--spacing-sidebar-w)` → `var(--spacing-sidebar-w-expanded)` across a
0.14 s transition), the browser re-rasterised the blurred shadow region on
every animation frame. On content-dense pages like the timetable (7×30
grid lines + events + overlays) that stalled the compositor. A border
costs nothing per frame, paints inside the already-contained subtree, and
preserves the visual separation. The transition duration was also
shortened from 0.28 s to 0.14 s (same commit) so fewer frames are painted
total; per-frame cost is unchanged but user-perceived lag is halved.

Both files now carry inline comments explaining the "don't re-introduce"
invariant for future maintainers — these comments double as grep sentinels
for the verify step below.

<task type="auto">
  <name>Task 3: Verify CSP allows non-hosted Supabase origins (local-dev unblocker)</name>
  <files>frontend/next.config.ts</files>
  <action>
PR #93 (commit c6ed6eb) extended the Content-Security-Policy's
`connect-src` directive in `next.config.ts` to conditionally include the
user's configured `NEXT_PUBLIC_SUPABASE_URL` when that URL does NOT match
`*.supabase.co`. The pre-fix CSP only whitelisted `https://*.supabase.co`
and `wss://*.supabase.co`, which blocked local flows where the developer
runs `supabase start` and points `NEXT_PUBLIC_SUPABASE_URL` at
`http://127.0.0.1:54321`. The conditional logic:

  1. Parse `NEXT_PUBLIC_SUPABASE_URL` (if set) → `supabaseOrigin`.
  2. `supabaseIsHosted` = true when the hostname matches `*.supabase.co`.
  3. If NOT hosted, build `supabaseExtraOrigins` containing the origin
     itself plus a ws(s)-rewritten variant (for Supabase Realtime
     WebSockets in local dev).
  4. Spread `...supabaseExtraOrigins` into the `connect-src` array
     alongside the existing hosted-Supabase entries.

The production whitelist for `*.supabase.co` is unchanged — the extra
origins are only appended when the env var explicitly points elsewhere.
This is a supporting fix (not a GPU paint-cost change) bundled into the
same retrospective because it shipped in the same session; the
development of the four main perf fixes required running `supabase start`
locally to verify behaviour without touching prod Supabase.
  </action>
